## Intent

Every task's `## Intent` section is free-form. **Two skeletons exist, and they already disagree:**

- `templates/task.md` prompts *"What changes, and why now."* and carries guidance under
  Acceptance criteria and Notes.
- `kit-task.sh:93` writes its own inline skeleton, with empty sections and none of that guidance.

So one shape has two homes, and they have drifted.

Anthropic's AI-native SDLC playbook (claude.com/blog/the-ai-native-sdlc-playbook) names what an
intent carries: *the problem, the proposed outcome, the users and systems affected, constraints,
and open questions*. It is captured in the originator's own words, and the product owner *"reviews
and corrects the agent-written `intent.md` before it is committed"*. **This task departs from the
playbook on purpose:** it keeps the intent as a section of the task file, not a separate
`intent.md`. A new mandatory file per change would add to the uniform chain depth the kit already
treats as a cost problem (`T-20260819-authoring-chain-depth-is-uniform-so-a-tr`).

**Who benefits:** whoever reads the task, human or agent. `skills/task-context` reads the whole task
file (`SKILL.md:32-33`), so it would get the problem, the constraints and the open questions stated,
instead of reconstructing them from the diff. No tool parses the Intent section. Tier floors come
from `paths:` and touches edges (`kit-index.sh:406`, `:1365`), and this task does not change that.

**Entry is covered automatically.** A task created from a brownfield entry proposal is made by the
operator running the `kit-task.sh` lines they accept (`docs/ENTRY-PROPOSAL.md:34`), and every
candidate carries that literal line (`:65`). So one skeleton reaches those tasks with no separate change.

It is plain markdown, so it belongs in the portable core and works for any coding agent.

## Acceptance criteria

- [ ] One skeleton for the body. `kit-task.sh` writes the task body from `templates/task.md`, or both
      come from one definition, so the two cannot drift again. The frontmatter stays generated by
      `kit-task.sh` from its flags, and the template's frontmatter matches what it emits, as
      documentation of the keys.
- [ ] The template is read with CR stripped, as `kit-init.sh:19-24` already does for the profile,
      and for the same reason: a file the kit writes into someone else's repository must land the
      same on every platform, including when the kit was fetched with `core.autocrlf=true`.
- [ ] The Intent section prompts for the five items as labelled lines for a human to fill in.
      They are a prompt, not a gate: existing task files are not rewritten, and nothing fails on a
      task that leaves them out. A check can follow later if the fields prove useful.
- [ ] Conformance:
      - a task created by `kit-task.sh` contains the template's Intent prompts;
      - restoring the inline skeleton fails the step;
      - with a CRLF template, the task file `kit-task.sh` writes contains no CR byte, and removing
        the CR strip fails the step.
